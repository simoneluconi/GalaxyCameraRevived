# Galaxy Camera 2 (EK-GC200): plan

Status: **LineageOS flashed and reaches boot_completed, but it is not usable yet** (2026-11-10, evening).

Open blockers, in order:
1. **"failed to prepare internal storage for system user"**: after the first boot, system_server cannot prepare user 0's storage. App data directories are missing (`/data/user_de/0/com.android.providers.telephony/databases`), so the persistent `com.android.phone` crash-loops. RescueParty then reboots to recovery with `--prompt_and_wipe_data` (or `--wipe_data`). The GC100 does not do this with the same fstab and keystore. Next: boot with `persist.sys.disable_rescue=true`, then read vold, installd and system_server around user unlock. The full first-boot logcats are in `device-dump/gc200-ourkernel/capture-*`, and the crash entries in /data/system/dropbox.
2. **eMMC after a warm reboot**: `mmc0: cmd_strt_bit not released`, no `mmcblk0`, and first-stage init then times out in `BlockDevInitializer::InitDevices`. It happens from Samsung's kernel into ours and, sometimes, from ours into ours; a battery pull always fixes it. The MSHCI driver, pdata and `exynos4_setup_mshci_init_card` match Samsung's GC200 kernel, so look at the controller clock and reset state the 2014 bootloader leaves behind.
3. **The recovery flag sticks**: an Android "reboot recovery" makes sboot keep booting recovery (`mach_board_main: recovery set!(0x80000)`, kept in PARAM) until a plain reboot from recovery. Samsung's recovery clears it; ours must never write PARAM, so `adb reboot` from the mini recovery is the way out.

Fixed the same evening: system_server waiting forever for a GNSS HAL (sf2wifi drops it from the manifest), the GNSS service crash loop that fired RescueParty (`SMDK4412_NO_GNSS`, smdk4412-common c2f4505), the Wi-Fi-only product (no messaging, Stk or APNs; sf2wifi ce250ab), and init's fatal reboots now go to recovery instead of download mode (kernel c3569d1b). `ro.product.model` still reads EK-GC100 (libinit_gd1 sets it). A GC200 on stock firmware was read without root (dumps in the git-ignored `device-dump/gc200-stock/`), then backed up from the mini recovery (docs/RECOVERY.md, GC200 section).

Done on 2026-11-10:
- **Kernel**: `CONFIG_MACH_SF2` on the GC1 board, `lineageos_sf2wifi_defconfig` (kernel `gd1` branch 03d328a5). Booted on the GC200 from BOOT with the mini recovery ramdisk: eMMC, Wi-Fi SDIO, touch, gpio-keys, LSM330, AK8963C, MAX17047/MAX77693, WM1811, panel, mDNIe and backlight all probe. No M9MO driver yet, so the ISP is never powered.
- **A warm reboot from Samsung's kernel into ours loses the eMMC**: pull the battery once after flashing from a stock-kernel boot (docs/RECOVERY.md).
- **Device tree** `device/samsung/sf2wifi` (local git, not on GitHub yet): builds `lineage_sf2wifi-ap2a-userdebug`. smdk4412-common lists sf2wifi among its devices (gd1 f4ed51d).
- **Blobs**: `vendor/samsung/sf2wifi` (local, never published) holds the GC200's Wi-Fi firmware and nvram and the Bluetooth `.hcd` files.

Still to do: flash and boot LineageOS; the touch orientation; GPS (the GC200 ships `gpsd` and `gps.default.so`, not the GC100's `gpsd_4752` and `gps.exynos4.so`, so the GC100 shims may not fit); the M9MO ISP driver (`m9mo_sf2.c`); RAM settings (the build still gets `ro.config.low_ram=true` and a 256m heap from the Go config); NFC tag; and the items below.

This page lists what the GC100 build already shares with a GC200 and what a GC200 build still needs, so the port can start without rewriting the GC100 tree.

## The ISP driver: do not use Samsung's `m9mo_sf2.c` (analysis 2026-11-10)

**Never build Samsung's `m9mo_sf2.c` as it is.** It can rewrite the ISP's flash on its own:
- `m9mo_init()` calls `m9mo_auto_fw_check()`. It is enabled for `CONFIG_MACH_GC1`, so it is live on the GC200, and it runs at every camera open.
- It is armed by a write to `/sys/class/camera/rear/rear_checkApp`, and any "newer" `RS_M9MO.bin` is then enough, looked for first on `/sdcard`.
- On the GC200 (system_rev 21) the update goes over SPI: `M9MO_SFW.bin`, then an erase of all 2 MB of the ISP flash and a rewrite. An oversized file also overflows a kernel buffer.
- Other write paths go through ioctls (factory shading data, calibration erase, lens EEPROM, debug writes, about 30 factory controls).
- With `ISP_LOGWRITE`, ISP timeouts write to /sdcard and can leave `set_fs(KERNEL_DS)` behind.

Its lens retraction is weaker than ours too:
- no shutdown hook, no time bound and no retry;
- it is skipped unless `POST_INIT` was sent, which our HAL never sends, so the lens would stay out.

**The plan**: keep our `m9mo.c`, with its firmware refusal and lens hardening, and add the few real SF2 differences under `#ifdef CONFIG_MACH_SF2`, about 100-200 lines:
- drive GPB(5)/GPB(6) (SPI NSS/MISO) low at probe;
- accept the 11-character `D16FL*` firmware version;
- an i2c read retry;
- `set_zoom` without the zoom-speed write and AF cancel;
- possibly the parameter-mode round trip around PASM changes, the pre-liveview write after a single shot and the init-target writes.

Unchanged from the GC100: the register map, 16 optical zoom steps, f-number limit 159, OIS, AF, the SMART_READ registers, the RAW path (CAPPARM 0x78, `YUVOUT_MAIN` 5, size 0x33), and the power sequence and regulators. Samsung's GC200 camera header renumbers enums (`RUNNING_MODE_RAW` 11, ISO and white balance values), so SF2 code must use our header, with any new values appended at the end. The full report is in the git-ignored `device-dump/gc200-notes/m9mo-sf2-report.md`.

## Facts from the GC200 (2026-11-10, stock, read over adb)

- **Identity**: codename `sf2wifi`, product `sf2wifixx`, board `smdk4x12`, `ro.hardware` smdk4x12. Android 4.3 (SDK 18), build JSS15J.GC200XXUCNK4, bootloader GC200XXUCNK4 (Nov 2014), CSC ITV. Kernel 3.0.31.
- **RAM**: MemTotal 1764560 kB (1.7 GB usable, against the GC100's 755 MB). Stock dalvik heap: 512m heapsize, 192m growth limit; density 320.
- **eMMC**: Samsung `M8G1GC`, manfid 0x15, oemid 0x0100, 8 GB, the same chip as the GC100. It is not on the kernel's brickbug list; the same caution applies.
- **ISP**: firmware `D16FLHB03DA` (the GC100 runs FCGB04). `/system/etc/firmware` holds `RS_M9MO.bin` (2 MB) and `M9MO_SFW.bin` (14 KB, new). Never let our kernel flash either.
- **Partitions** (`dw_mmc`, sizes in KB), the GC100's layout with a bigger SYSTEM and DATA:

  | p | name | KB | GC100 |
  |---|---|---|---|
  | 1, 2 | BOTA0, BOTA1 | 4096 each | same |
  | 3 | EFS | 20480 | same |
  | 4 | PARAM | 8192 | same |
  | 5, 6 | BOOT, RECOVERY | 8192 each | same |
  | 7 | RADIO | 32768 | same size, though the GC200 has no modem |
  | 8 | CACHE | 1048576 | same |
  | 9 | SYSTEM | 2097152 | 1572864 |
  | 10 | HIDDEN | 368640 | same (our /vendor) |
  | 11 | OTA | 8192 | same |
  | 12 | TDATA | 204800 | not on the GC100 |
  | 13 | USERDATA | 3813376 | 4337664 |

- **Keys**: `gpio-keys` declares the same codes as the GC100: KEY 0x74 (power), 0x210, 0x215, 0x216, 0x220-0x222, 0x240, and SW 0x0f (flash pop-up). Input devices: gpio-keys, sec_touchscreen, Midas_WM1811 jack, gyro_sensor, compass_sensor.
  - Checked with getevent: they behave as on the GC100, so `keylayout/gpio-keys.kl` fits as is. Half press 0x210 (FOCUS), full press 0x220 nested inside it; zoom lever T 0x215 with the fast stage 0x221 nested inside, W 0x216 with 0x222; flash up is SW 0x0f = 1. No lens-ring events were seen (0x240 never fired).
- **Wi-Fi/BT**: bcmdhd firmware `*.bin_b2`, nvram `nvram_net.txt` plus `_bv` and `_murata` variants, BT `bcm4334.hcd`, `_murata` and `_semco`.
- **Other**: `gpsd` (BCM4752), MobiCore (`mcDriverDaemon`), an NFC tag IRQ (`irq/400-nfc_tag`), `fimc_is_fw.bin` and `mfc_fw.bin` in /system/vendor/firmware.

## Hardware: same and different

The GC200 is the GC100's successor (2013, Android 4.3). It keeps most of the hardware:

| Part | GC100 (gd1) | GC200 |
|---|---|---|
| SoC | Exynos 4412 | Exynos 4412 |
| RAM | 1 GB (768 MB usable) | 2 GB |
| ISP and lens | Fujitsu M9MO, 21x 23-481 mm | M9MO family, same 21x lens. Samsung's kernel has a separate driver, `m9mo_sf2.c` |
| Panel and touch | s6d6aa1 4.8" 720p, Melfas GC touch | same |
| Wi-Fi/BT | BCM4334 | BCM4334 |
| GPS | BCM4752 | BCM4752 |
| Sensors | LSM330DLC, AK8963C | same |
| PMIC, fuel gauge, codec | MAX77686/77693, MAX17047, WM1811 | same |
| Modem | XMM6262, 3G | **none** (Wi-Fi only) |
| NFC | no | yes |
| Kernel board | `MACH_GC1` | `MACH_GC1` + `MACH_SF2` |

Kernel source for reference: gitlab.com/eloydegen/kernel-samsung-ek-gc200 (Samsung's GC200 release).

## What is already shared

Since 2026-11-04 the device tree `device/samsung/gd1` is split:

- **`common.mk`** (product) and **`BoardConfigCommon.mk`** (board):
  - the camera HAL, sensors HAL, GPS, audio, health;
  - the camera-first app set, with GC Gallery, the removed packages and the home layout;
  - the display rotation, density and touchscreen idc;
  - the SELinux bring-up settings, the vendor sepolicy and the storage settings.
- **`gd1.mk`** and **`BoardConfig.mk`** (GC100 only):
  - the RIL and telephony feature;
  - the partitions and the fstab/init files;
  - the gpio key map;
  - the kernel defconfig;
  - the 768 MB RAM settings (dalvik heap, low_ram, trim limits);
  - the vendor blobs, OTA assert and init library.
- `Android.mk` builds the tree's modules whenever `TARGET_GALAXYCAMERA_COMMON` is set (BoardConfigCommon.mk), not only for `gd1`.

Both apps were audited for GC100-only assumptions (2026-11-04; details in CAMERA-APP.md and GALLERY-APP.md §1). Both find the camera folder as `DCIM/GC<3 digits>/`. Both tell the zoom lever's fast stage by scan codes 545/546: a GC200 key map should keep those codes.

## What a GC200 build needs

1. **Facts from a real GC200**, read without root like the GC100 dumps:
   - `getprop` (the codename `ro.product.device`, the board);
   - `/proc/partitions`, the by-name map and partition sizes;
   - getevent for the keys, including the zoom ring;
   - the ISP firmware version.
   Also the stock firmware (SamMobile) for the blobs. Never flash a PIT: plan within the stock layout, as on the GC100.
2. **Kernel**:
   - port the `MACH_SF2` board bits and `m9mo_sf2.c` from Samsung's GC200 source into our kernel (branch gd1), next to the GC100's;
   - add a `lineageos_<codename>_defconfig`.
   Keep every GC100 rule for the GC200: no ISP firmware update, the lens retract on release, no touch firmware update.
3. **Device tree** `device/samsung/<codename>`. Its makefiles:
   - `BoardConfig.mk` includes `device/samsung/gd1/BoardConfigCommon.mk`, then sets the partitions, defconfig, fstab and OTA assert;
   - `<codename>.mk` inherits `device/samsung/gd1/common.mk`, then adds the fstab/init files, the key map, the NFC packages if wanted, and the 2 GB RAM settings (probably no `low_ram`);
   - `lineage_<codename>.mk` inherits `aosp_base.mk`, not `aosp_base_telephony.mk`, and gets no RIL.
   - No modem means no SMS either: remove the `messaging` app there (the GC100 keeps it in gd1.mk, so common.mk's RemovePackages no longer lists it).
   Once that works, the shared files can move into their own repo (for example `device/samsung/galaxycamera-common`) with a plain `git mv`; nothing in them names gd1 except `COMMON_PATH` and a few file names.
4. **Camera HAL**: check that the M9MO preset in `camera/exynos_camera.c` matches what `m9mo_sf2.c` exposes:
   - the CIDs, the RAW mode, and the SMART_READ registers;
   - the zoom steps and the f-number range.
   Differences go behind a property or a build flag, not a copy of the HAL.
5. **Vendor blobs**: extract them with `extract-files.sh` from the GC200 stock system, like `tools/mk-blobsrc.sh` does for the GC100. Keep using the GC200's own Wi-Fi/BT calibration (`nvram_net.txt`, `.hcd`).
6. **Wi-Fi 5 GHz check.**
   - The GC200 has the same BCM4334: Samsung's `sf2wifi_00_defconfig` sets `CONFIG_BCM4334=y`.
   - On the GC100, 5 GHz receives but never transmits ("JOIN: authentication failure, no ack"; docs/TODO.md).
   - A GC200 running our kernel's bcmdhd tells the two causes apart:
     - if 5 GHz works there, the GC100 fault is that unit's hardware;
     - if it fails the same way, it is our driver.
   - Turn on `echo 1 > /sys/module/dhd/parameters/gd1_wl_debug` and `dhd_console_ms` for the first 5 GHz join.
